# OralCompass: codeLinc 11, Path 1 (Dental)

*Your care journey. Your coverage. Clearly mapped.*

OralCompass is a mobile app. Install it to your phone's home screen and it opens full screen, like any other app on the phone. It paints
a person's dental treatment as a sea passage (each procedure an island, each insurance rule a checkpoint on the route) and their dental
plan as a coast of landmarks (Your plan, Deductible, Coverage, Annual maximum, Cost breakdown). Both maps fill the screen edge to edge.
<!-- verify: feat/mobile-cinematic -->

Every dollar on the cost trail, from the dentist's fee to "you pay", is computed by a deterministic engine in integer cents and stitched to
the exact clause (document label, page, quote) that produced it. Where a document is silent the app says "Not stated in this document"
instead of filling in a typical value. Before any AI reads an uploaded document, personal details (names, addresses, member IDs, dates of
birth and more) are found on the phone and taken out, and the app shows how many: "12 personal identifiers removed before AI analysis".
<!-- verify: feat/client-redaction -->
A prompt box on every tab answers questions about the plan in simple terms first. <!-- verify: feat/ask-plain -->

It is information only: it explains what the documents say and what the arithmetic yields, and the person makes every decision with their
dental team.

## Install it on a phone

OralCompass is an installable web app (`web/public/manifest.webmanifest`: `display: standalone`, home-screen icons, `theme-color`;
`web/index.html`: `viewport-fit=cover`, `apple-mobile-web-app-capable`, `apple-touch-icon`).

- **iPhone (Safari):** open the app's address, tap Share, then **Add to Home Screen**. The icon opens OralCompass without browser bars.
- **Android (Chrome):** open the menu and choose **Install app** (Chrome offers installation over HTTPS or on `localhost`; on a plain LAN
  address it adds a shortcut that opens in a browser tab).
- **On a laptop or tablet:** the same phone app renders in a centered column (at most 480 px wide) while the painted journey fills the
  window behind it, dimmed by a vignette and an ink scrim. There is no separate desktop layout. <!-- verify: feat/mobile-cinematic -->

The app needs its server: the service worker (`web/public/sw.js`) exists only for optional reminders (Web Push), has no fetch handler and
caches nothing, so OralCompass does not work offline.

## 60-second start

Requirements: Python 3 (the container uses 3.12), Node 22 with npm (the container build stage uses node:22), and a browser at or above the
Tailwind v4 floor (Safari 16.4+, Chrome 111+, Firefox 128+).

```bash
# 1. Environment. api/.env is gitignored; never commit it.
cp api/.env.example api/.env
#    Demo mode (no key, no model call): set ORALCOMPASS_LLM_PROVIDER=none, or leave OPENROUTER_API_KEY empty.
#    Live mode: ORALCOMPASS_LLM_PROVIDER=openrouter, ORALCOMPASS_LLM_MODEL=anthropic/claude-haiku-4.5, OPENROUTER_API_KEY=<your key>.

# 2. API (terminal 1). Shell variables override api/.env, so this line forces demo mode even with a live .env.
cd api && pip install -r requirements.txt
ORALCOMPASS_DEV_AUTH=1 ORALCOMPASS_LLM_PROVIDER=none ORALCOMPASS_DATA_DIR=$(mktemp -d) \
  python3 -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# 3. Web (terminal 2). npm run dev / build / preview copy ../fixtures (plans + PDFs, including the
#    fictional sample statement) into the gitignored web/public/fixtures first (web/scripts/copy-fixtures.mjs).
cd web && npm install
npm run dev            # http://localhost:5173, proxies /api to 127.0.0.1:8000
```

Open the app and choose **Open a labeled sample journey: Alex Chen** (real public plan rules) or **Sam Rivera** (fictional plan with a stored PDF).

- **On a real phone:** run the one-server command below with `--host 0.0.0.0` on a trusted network and open `http://<laptop-address>:8000`
  on the phone (same Wi-Fi), then add it to the home screen. Session cookies are marked `Secure` only over HTTPS, so plain HTTP on a LAN works.
- **Live mode** is the same API command without `ORALCOMPASS_LLM_PROVIDER=none`. Live extraction of the 14-page Harborview fixture
  takes minutes; demo mode returns the cached fixture extraction for the fictional PDFs (matched by checksum) and labels itself.
- **One server, as a presenter would run it:** `cd web && npm run build && cd ../api && ORALCOMPASS_DEV_AUTH=0 ORALCOMPASS_LLM_PROVIDER=none
  python3 -m uvicorn app.server:app --host 127.0.0.1 --port 8000`, then open http://127.0.0.1:8000 (signed cookie sessions, API under `/api`).
- **Other ports:** `ORALCOMPASS_API_TARGET=http://127.0.0.1:<port>` points the Vite dev/preview proxy at another API;
  `ORALCOMPASS_WEB_BASE=http://127.0.0.1:<port>` points the screenshot and layout tools at another preview.
- **Screenshot walk:** `cd web && npm run build && npx vite preview --port 4173 --host 127.0.0.1`, then from the repo root
  `python3 tools/screenshots.py shots/` (phone devices plus the wide-screen column, reduced motion; the walk sends the dev header itself).
  `shots/` is scratch output.

A production bundle served by `vite preview` sends no `X-Dev-User` header, so against a dev-auth API it gets 401 unless it was built with
`VITE_DEV_AUTH=1 npm run build`. The phone-first demo script with exact taps is `docs/DEMO_SCRIPT.md`.

## Feature tour, by tab, on a phone

Three tabs sit in the bottom dock: My journey, My plan, Documents. Changing tabs scrolls the new tab to the top and moves focus to
its heading. Details open in bottom sheets that leave the dock reachable. <!-- verify: feat/mobile-cinematic -->

### The cinematic painted map

<!-- verify: feat/mobile-cinematic (this whole subsection) -->
Both maps are painted plates that run edge to edge across the app, with no box, border or rounded frame around them. Each starts just
under a compact header and dissolves into the parchment at its bottom edge. A title card sits over the painted sky with the two strongest
facts. On the first view in a session the camera makes an establishing shot (the painting settles from a slight zoom while the route
draws); afterwards the plate drifts very slowly. Tapping an island or landmark moves the camera so the selection sits above the bottom
sheet, and closing the sheet moves it back. Motion is transform and opacity only, pauses when the app is hidden, and with reduced motion
the app shows the end states directly (`web/src/components/atlas/CinematicStage.tsx`).

**My journey.** A short title and one facts line (checkpoints completed, what you pay, what the plan pays, with its calculated label);
the other summary rows sit in a "Journey details" disclosure below the map. <!-- verify: feat/mobile-cinematic --> The Passage runs down the
painting: START pier, one island per procedure (Narrow Strait, High Cliffs, ...), insurance checkpoints along the route (fee, allowed amount,
deductible, annual maximum, plan share, you pay), soundings between islands that show the deductible and maximum left, and Harbor Light
with the totals. Procedures the plan does not cover sit in the margin as a closed channel; missing inputs show as fog. Tapping an island
opens the procedure sheet: procedure as written, allowance, coverage share, waiting period, alternate benefit, annual maximum, and the
final cost, with the dollar pipeline rolling each step. The care timeline and the answers log follow below the map as list sections.

**My plan.** The same map concept as My journey: the five landmarks are painted stops on the same inked route down the coast, each label
showing the familiar term first, the place name small, and the value with its evidence badge or stitch. <!-- verify: feat/mobile-cinematic -->

| Landmark | Place on the coast | Painted as |
|---|---|---|
| Your plan | The harbor | The START pier with the boat |
| Deductible | The bridge | An island with an inked bridge |
| Coverage | The cove | A second island plate, flipped and tinted |
| Annual maximum | The lookout | The large island plate |
| Cost breakdown | The lighthouse | The lighthouse island |

Tapping a landmark opens its sheet, which reads at three depths: plain words, your numbers, then the exact wording with its page.

The benefits compass and the plan pickers follow below the map. Two ways to load a plan: pick a preset (real or fictional), or **upload a
plan document**: personal details removed on the device (next section), extraction stages, a review table where each field shows its quote
and verification state, then **Publish this plan version** creates an immutable `UP1`, `UP2`, ... that loads through the same engine.

**Documents.** The clause list for the active plan as list rows, a pdf.js page view for stored PDFs with the stitch highlighted, and an
honest note when a real plan's PDF is not stored (the official link is shown instead). The upload wizard and reminders open in bottom sheets.

### Personal details removed before AI analysis

<!-- verify: feat/client-redaction (this whole subsection) -->
When a plan document or benefits statement is picked, OralCompass reads it on the phone first, before anything is uploaded.

1. **Detection on the device.** The browser reads each page's text layer with pdf.js and runs a deterministic detector
   (`web/src/lib/redact.ts`) for ten kinds of personal detail: names (after a label such as Patient, Member, Subscriber, Insured, Employee,
   Dependent, Policyholder, Name, Dear or Attn, and every later occurrence of the same name), street addresses and "City, ST ZIP" lines,
   member IDs, group numbers, claim numbers, account numbers, Social Security numbers, dates of birth, personal phone and fax numbers, and
   email addresses. It leaves alone what the AI needs: procedure codes (D0120, D2740, ...), dollar amounts, percentages, plan dates,
   deductible and maximum figures, frequency limits, waiting periods, tooth numbers, plan and carrier names, and the carrier's toll-free
   numbers. The count is of distinct identifiers; a name printed on every page counts once.
2. **The review step.** Before upload the screen says, with the real count: **"12 personal identifiers removed before AI analysis"**
   ("1 personal identifier ..." for one; "No personal identifiers found. The AI receives the plan text as is." for none). Below it: chips by
   kind ("2 names · 2 addresses · 1 member ID · ..."), a list of every identifier with its value masked (a Show toggle reveals it on the
   phone), "removed in N places", and a **Keep in text** switch for anything that is not personal (the count updates). A field adds any
   other word or number to remove, and a preview shows the text with each removal as a small inline token such as `[member ID removed]`.
3. **Upload and the server re-check.** **Continue** stores the PDF in the person's private space and sends the confirmed identifiers with
   it. Before any model call the server removes every occurrence of every confirmed value from the text it reads (whatever the case,
   spacing or line breaks), then runs its own patterns for the same ten kinds as a safety net (`api/app/redaction.py`). After upload, the
   extraction progress ("Removing personal details · 12 removed"), the review table and the Documents card show the server's count, and say
   so when the server's own check found more.
4. **What the AI receives.** Only that cleaned text: coverage clauses, deductible, annual maximum, procedure codes, percentages,
   exclusions, waiting periods and limits. Quotes are still verified against the PDF's own pages. The details are in `docs/SECURITY.md`
   ("Redaction before AI analysis"), including what this cannot catch.

The treatment-plan reader applies the same on-device step to pasted text and to PDFs with a text layer. A photo or scanned page cannot be
redacted; it is sent only after the person confirms a notice that says so.

### Ask in plain words

<!-- verify: feat/ask-plain (this whole subsection) -->
Every tab has a prompt box: a single "Ask in plain words" field just above the dock. Tapping it opens a bottom sheet with the composer
("Ask anything about your plan, in your own words"), four suggestions in everyday language that depend on the tab (on My plan, for
example: "What is a deductible?", "What does plan share mean?", "What is an annual maximum?", "What is a waiting period?"), and the
answers below as parchment notes, not chat bubbles.

- **Simple terms first.** Every answer opens with one or two short sentences in everyday words, around an 8th-grade reading level, with
  insurance words explained in passing ("your deductible (the part you pay before the plan starts paying)"). Amounts carry their evidence
  badge, for example "Your plan's deductible is ..." with the plan document's badge and stitch.
- **The details stay one tap away.** The steps, clauses and where each figure comes from sit under **Show the details**, closed by default.
- **Say it more simply.** A button on each answer asks again for an even plainer, one-sentence version.
- **What it can answer:** what a term means (a glossary of US dental benefit terms such as deductible, plan share, allowed amount, annual
  maximum, waiting period, frequency limit, in-network and out-of-network, alternate benefit, exclusions, predetermination, EOB, procedure
  code, copay, balance billing, benefit year; `api/app/assistant_glossary.py`), what you and the plan pay for the planned work, why one
  procedure on the journey costs what it does, how much deductible and annual maximum are left, and what a document
  covers.
- **Guards.** Questions are classified deterministically first. It never computes: every amount is a pointer into the engine's ledger.
  A "should I" question gets "OralCompass explains what your documents say; it does not choose for you." followed by what the document says;
  a clinical question gets "This is a question for your dentist; OralCompass only explains your plan and your costs." In live mode the
  model only rewrites the simple sentence around the same figures, and an answer that reads above a 9th-grade level falls back to the
  template. Demo mode answers the same questions with templates and no key.

The procedure sheet's "Ask about this step" and the clause card keep their own scoped questions.

### The AI features (all optional, all with a deterministic fallback)

| Feature | What the model may do | What keeps it honest |
|---|---|---|
| **Extraction with quote verification** (`api/app/extraction.py`, `uploads.py`) | Return the sentences that state each field, with pages, then structure them. It never names an internal procedure key and never computes. | Only text with personal details removed is sent: the values confirmed on the device plus the server's own patterns. <!-- verify: feat/client-redaction --> Every quote is checked against the cited page's text: exact match is *confirmed*, a match within ±2 pages or similarity ≥ 0.92 is *likely* (needs review), anything else is dropped. Wording maps to the 16 fixed procedure keys only through printed vocabulary. Text addressed to automated readers inside a document is removed and listed, never used. |
| **Grounded assistant and Ask in plain words** (`api/app/assistant.py`) | Phrase the simple sentence over facts that read-only, owner-scoped tools gathered first. <!-- verify: feat/ask-plain --> | Amounts appear only as `{{ref:n}}` placeholders resolved from the engine's ledger; every sentence needs a grounding ref and passes the runtime advice guard; advice and clinical questions get fixed templates; a readability check falls back to the template. <!-- verify: feat/ask-plain --> Demo mode uses templates over engine fields. |
| **Treatment-plan reader** (`api/app/treatment_reader.py`) | Read each line of a pasted estimate or a photo *as written* (wording, tooth, fee, code). | Pasted text and PDF text layers are redacted on the device and again on the server before any call. <!-- verify: feat/client-redaction --> Images are re-encoded to strip EXIF and are sent only after the visitor confirms the image-consent notice (an image cannot be redacted). Lines become treatment items only after the person confirms them. |
| **Clause explainer** (`api/app/explain.py`) | Write one sentence of at most 25 words from one cited clause's quote. | Every number in the sentence must appear in the quote, one content word must be shared, the advice guard runs; any failure returns the plain template. |

Every live call first reserves a request with the cost guard (`api/app/llm_guard.py`): per-visitor limits per kind (extraction 5/day,
reader 10/day, explainer 60/day, assistant 30 per 10 minutes) and global daily caps (300 requests, US$2.00 estimated spend by default).
A refusal falls back to demo behaviour and the UI says so.

### Demo mode and the fictional sample statement

Demo mode (`ORALCOMPASS_LLM_PROVIDER=none`, or no key) needs no key and makes no model call: the assistant answers from templates, and an
upload whose SHA-256 matches a stored fixture runs the full extraction from that fixture, still verifying every quote against the uploaded
file's pages.

<!-- verify: feat/client-redaction -->
The upload step offers **Try a fictional sample statement**: a made-up four-page member benefits statement for the fictional TW26 plan
(`fixtures/documents/tw26_fictional_sample_statement.pdf`, generated by `tools/make_sample_statement.py`). It carries exactly 12 invented
personal identifiers (member and dependent names, a street address and a city/state/ZIP line, member ID, group number, date of birth, an
SSN-style subscriber number, a personal phone number, an email address, a claim number and an account number), repeated in the header of
each page, next to the plan's real numbers, procedure codes, plan dates and the carrier's toll-free number. The sample runs the same
on-device path as any picked file, so the review step shows "12 personal identifiers removed before AI analysis", the toll-free number and
plan dates stay in the text, and the demo extraction fixture carries it through review to **Publish this plan version**. Tests assert the
detector finds exactly those 12 and nothing else.

## How the numbers are computed

- **One engine.** All money lives in `engine/oralcompass_engine` (stdlib Python, integer cents): deductible scope, coinsurance, annual
  maximum caps (including "Unlimited"), separate out-of-network deductible and maximum, alternate benefit, procedure-scoped waiting periods,
  frequency clocks, exclusions, balance billing, ranges and "what moves these numbers". The API and the model never do arithmetic.
- **A ledger of steps.** Each estimate is a list of steps with a rule code and the clause that produced it; the web cost trail renders those
  steps and stitches each one to its page and quote.
- **Missing input stays missing.** An input that is not known makes the step `unresolved`, names the missing input and how to obtain it, and
  turns a single figure into a range (Sam: $640 to $665 when the remaining deductible was not provided).
- **Evidence badges on every number:** DOC (label, page, quote), USER, ASSUMED (a hypothetical the person typed), AMBIGUOUS, UNKNOWN
  ("Not stated in this document" or "Not provided"), CONFLICT (both excerpts and dates shown, never resolved by picking one).

## Deployment

Deployment-ready, not deployed. `Dockerfile`, `railway.json` and `api/.env.production.example` describe one container that serves the
API at `/api` and the built web app at `/`, with signed HttpOnly session cookies, a SQLite store on a volume, CSP and body limits, ids-only
logs, and the live-AI cost guard. Served over HTTPS, the same address installs on Android and iPhone home screens. `docs/DEPLOY.md` has the
steps and states what is not production-grade; `docs/SECURITY.md` states what reaches a model.

## Limitations (stated, not hidden)

- Real plan PDFs are not stored in this repository; their clauses are quoted with pages and the official link. NCFlex certificate clauses
  past p.51 and FEDVIP brochure pages past about p.30 are UNKNOWN. DD24 is a 2024 document.
- No accounts: records are tied to one browser's session cookie. One instance, one SQLite file. No offline mode.
- Personal-detail removal is pattern-based (on the device and on the server) plus the person's own terms. It finds names after a label,
  so a name written only in running prose, with no label anywhere in the document, is missed unless the person adds it; unusual formats
  can be missed too. A scanned PDF or a photo has no text to read, so nothing can be removed from it (a plan PDF with no text layer is not
  sent to a model; a treatment-plan photo is sent only after the consent notice). There is no OCR redaction and no image cropping.
  <!-- verify: feat/client-redaction -->
- The uploaded PDF itself is stored, unredacted, in the person's private data directory (quotes are verified against it and the page view
  shows it) until "Delete all my data".
- Live-AI spend is an estimate from reported token usage, not the provider's bill.
- Web Push needs VAPID keys and is unverified end to end. Docker image build and container smoke have not been run where this was built.
- `infra/template.yaml` is an AWS SAM skeleton (Cognito, KMS, S3) and is not what the container uses.
- No certifications are claimed. OralCompass is not a HIPAA-compliant service and makes no compliance claim.
- Open items are tracked in `docs/BUILD_FOLLOWUPS.md`.
